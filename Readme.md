# Отчет по лабораторной работе: Расчет определенного интеграла методом Монте-Карло в многопоточной среде с использованием разделяемой памяти

## 1. Описание задачи и математическая модель
Целью работы является численный расчет определенного интеграла заданной аналитической функции f(x) = x³ на промежутке [0; 2] методом Монте-Карло с организацией параллельных вычислений в n потоков.

### Математическое основание:
* **Точный аналитический интеграл:** 
  \[\int_{0}^{2} x^3 \,dx = \left. \frac{x^4}{4} \right\vert_{0}^{2} = \frac{16}{4} = 4.0\]
* **Область значений функции на заданном отрезке:** [0; 8].
* **Параметры области интеграции (ограничивающего прямоугольника):** 
  Ширина = 2.0, Высота = 8.0, Площадь (\(S_{box}\)) = 2 × 8 = 16.0.

## 2. Архитектура программного комплекса
Проект реализован на языке **C (стандарт C11)** с использованием библиотеки **POSIX Threads (`pthread.h`)** и механизмов межпроцессного взаимодействия через разделяемую память POSIX (`shm_open`, `mmap`). Комплекс состоит из двух независимых модулей:

* **Программа А (Вычислитель):** Создает n рабочих потоков (`worker`), каждый из которых генерирует N/n случайных точек в прямоугольнике с помощью потокобезопасного генератора `drand48_r`. Программа фиксирует чистое время работы потоков и сохраняет результаты попаданий под кривую в общую память.
* **Программа Б (Сборщик результатов):** Инициализирует сегмент разделяемой памяти (Shared Memory) и, дождавшись окончания работы Программы А, вычисляет финальное значение интеграла на основе собранных данных.

### Модели хранения результатов и синхронизации:
1. **Вариант `no_sync` (Независимые ячейки):** В структуре разделяемой памяти выделен массив `local_hits[MAX_THREADS]`. Каждый поток инкрементирует свой локальный счетчик и записывает его в персональную ячейку памяти **один раз** в самом конце работы. Синхронизация отсутствует.
2. **Вариант `with_sync` (Разделяемая ячейка):** Все потоки делят одну общую переменную `global_hits`. Каждый инкремент защищен межпроцессным мьютексом POSIX (`PTHREAD_PROCESS_SHARED`). Для демонстрации эффекта конкуренции за ресурсы (Lock Contention) блокировка мьютекса вынесена **внутрь** вычислительного цикла потока.

## 3. Инструкция по сборке, запуску и визуализации

### Требования к окружению:
* Операционная система Linux (или среда WSL на Windows).
* Установленный компилятор `gcc` и утилита `make`.
* Интерпретатор `python3` с установленной библиотекой `matplotlib` для построения графиков.

### Шаг 1. Компиляция проекта
Для автоматической сборки всех четырех исполняемых файлов выполните в корневой папке проекта команду:
```bash
make
```

### Шаг 2. Запуск автоматического тестирования
Чтобы провести полную серию измерений для всех конфигураций потоков (1, 2, 4, 8, 16, 32) без ручного переключения окон, запустите встроенный в `Makefile` бенчмарк:
```bash
make test_all
```

### Шаг 3. Построение графиков эффективности
После выполнения тестов и фиксации результатов запустите Python-скрипт для генерации графиков времени выполнения и коэффициента ускорения:
```bash
# Установка библиотеки для графиков (если отсутствует)
pip install matplotlib

# Запуск скрипта визуализации
python3 plot_results.py
```
Скрипт выведет графики на экран и автоматически сохранит их в текущую директорию в файл высокого разрешения под именем `performance_charts.png`.

### Шаг 4. Очистка временных ресурсов
После завершения исследования принудительно удалите исполняемые файлы и очистите оперативную память системы от виртуальных файлов Shared Memory одной командой:
```bash
make clean
```

## 5. Анализ результатов и ответы на задачи исследования

### Задача 1: Оценка прироста производительности и определение числа ядер
На основе анализа масштабируемости алгоритма без синхронизации установлено, что **исследуемая машина обладает 4 физическими ядрами**. 
* При переходе от 1 к 2 потокам наблюдается практически идеальное линейное ускорение: S(2) = 1.95.
* При переходе от 1 к 4 потокам эффективность параллелизма сохраняется на высоком уровне, достигая ускорения S(4) = 3.44.
* Начиная с n = 8, темп прироста производительности резко ломается. Дальнейшее падение времени на 16 и 32 потоках обеспечивается за счет технологии Hyper-Threading (логических ядер), однако оно уже не имеет линейного характера, так как физические вычислительные блоки процессора (ALU) полностью загружены.

### Задача 2: Наблюдение стагнации роста и оценка накладных расходов

1. **Стагнация в режиме без синхронизации (`no_sync`):**
   При увеличении числа потоков сверх количества логических ядер процессора (n=16 → 32) время выполнения практически перестает снижаться (0.154 с и 0.142 с соответственно). График времени выходит на плато. Накладные расходы ОС на **переключение контекста (Context Switching)** начинают полностью нивелировать выгоду от дальнейшего распараллеливания.

2. **Влияние синхронизации на производительность (`with_sync`):**
   В серии тестов с использованием мьютекса внутри цикла обработки точек выгода от многопоточности полностью уничтожается. Несмотря на то, что объем обрабатываемых данных (N) был уменьшен **в 10 раз**, время работы программы монотонно возрастает: с 0.124 с (1 поток) до 0.307 с (16 потоков).
   * **Критическая точка:** Накладные расходы от использования синхронизации начинают превосходить преимущества параллелизма **сразу же при n ≥ 2**.
   * **Причина:** Возникает состояние жесткой конкуренции за замок (**Lock Contention**). Потоки большую часть процессорного времени проводят в заблокированном состоянии, ожидая освобождения мьютекса для инкремента единой ячейки памяти. Непрерывный перевод потоков из состояния исполнения в режим ожидания (и обратно) создает колоссальные накладные расходы на уровне ядра ОС.

## 6. Заключение
Экспериментально подтверждено, что для вычислительных задач типа Монте-Карло критически важна изоляция потоков по памяти. Архитектура с **независимыми ячейками памяти** обеспечивает эффективное масштабирование параллельных вычислений вплоть до исчерпания физических ядер CPU. Напротив, использование **одной разделяемой ячейки памяти** с синхронизацией внутри интенсивных циклов приводит к катастрофическому падению производительности из-за накладных расходов на Lock Contention.
