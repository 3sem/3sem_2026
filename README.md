
Сравнительный анализ производительности механизмов IPC в Linux


📋 Описание проекта

Данный проект исследует эффективность работы трех механизмов межпроцессного взаимодействия (Inter-Process Communication, IPC) в операционной системе Linux при передаче больших потоков данных (~100 МБ) с использованием различных размеров буфера приложения.
Исследуемые инструменты:
1. Разделяемая память System V (SHM) с синхронизацией на базе семафоров (semop).
2. Очереди сообщений System V (MSG Queue).
3. Именованные каналы (FIFO).

Измерения проводятся для файла размером 100 МБ (input.dat), сгенерированного из случайных данных (/dev/urandom). Целостность переданной информации жестко валидируется путем сравнения хэшей md5sum исходного и полученного файлов.
Замер времени выполнения участка передачи данных реализован внутри C-кода с использованием высокоточного таймера clock_gettime(CLOCK_MONOTONIC, ...) из заголовочного файла <time.h>.


Характерные размеры буфера:

• а) Малый буфер (4096 байт / 4 КБ): Соответствует типичной нижней границе лимита одного сообщения для очередей (MSGMAX).
• б) Средний буфер (65536 байт / 64 КБ): Соответствует стандартной емкости буфера пайпа/FIFO в ядре Linux по умолчанию.
• в) Большой буфер (1048576 байт / 1 МБ): Существенно превышает стандартную системную емкость FIFO.


📈 Результаты измерений

На основе проведенных практических испытаний зафиксированы следующие временные показатели (в секундах):

Механизм IPC	Буфер 4 КБ (Малый)	Буфер 64 КБ (Средний)	Буфер 1 МБ (Большой)
SHM	8.6075 сек	1.5211 сек	1.0354 сек
MSG Queue	4.1786 сек	3.6983 сек	3.7295 сек
FIFO	4.0816 сек	0.9852 сек	1.1996 сек


Визуализация данных (Гистограммы) находится в файле Figure_1.png

• Разделяемая память на буфере 4 КБ показала худший результат (8.6 сек) — в 2 раза медленнее конкурентов.
• Причина: Сама по себе SHM осуществляет передачу данных со скоростью ОЗУ. Однако она требует внешней синхронизации. Программа использует семафоры System V (semop). При буфере 4 КБ количество системных вызовов к ядру для блокировки/разблокировки становится колоссальным. Затраты ядра на переключение контекста полностью нивелируют аппаратную скорость памяти. С ростом буфера до 1 МБ частота вызовов семафоров падает в 256 раз, выводя SHM в лидеры (1.03 сек).

• Время работы MSG Queue осталось неизменным (~3.7 сек) независимо от размера буфера приложения.
• Причина: В ядре Linux максимальный размер атомарного сообщения жестко ограничен (/proc/sys/kernel/msgmax, обычно 8 КБ). Программа вынуждена принудительно дробить буферы приложения в 64 КБ и 1 МБ на системные кванты по 4 КБ внутри цикла msgsnd. Следовательно, нагрузка на ядро не падает при увеличении буфера в коде пользователя. MSG Queue не подходит для трансляции тяжелых файловых потоков.

• FIFO демонстрирует наилучшее время работы (0.98 сек) именно на буфере среднего размера (64 КБ), обгоняя даже SHM. На буфере 1 МБ скорость FIFO незначительно падает (до 1.20 сек).
• Причина: Размер внутреннего кольцевого буфера FIFO в ядре Linux составляет ровно 64 КБ. Когда размер буфера пользовательского приложения идеально совпадает с размером системного буфера, планировщик Linux работает в резонансе — операции read/write выполняются без избыточных блокировок и промежуточного дробления страниц. При буфере в 1 МБ ядро вынуждено принудительно приостанавливать пишущий процесс прямо посреди одного системного вызова, пока читатель не освободит место, что создает микрозадержки.
