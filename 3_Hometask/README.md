## Сборка:
```
# Разделяемая память SYS V:
gcc -O2 -Wall -Wextra -D_GNU_SOURCE -D_FILE_OFFSET_BITS=64 main.c common.c sharedMemory.c -o shm_transfer

# Очередь сообщений SYS V:
gcc -O2 -Wall -Wextra -D_GNU_SOURCE -D_FILE_OFFSET_BITS=64 main.c common.c messageQueue.c -o mq_transfer

# Именованные каналы (FIFO):
gcc -O2 -Wall -Wextra -D_GNU_SOURCE -D_FILE_OFFSET_BITS=64 main.c common.c fifo.c -o fifo_transfer
```

## Запуск тестов:

### Создание передаваемого файла:
```
dd if=/dev/urandom of=<file_name> bs=1048576 count=4096
```

### Увеличение ограничений очередей сообщений:

```
sudo sysctl -w kernel.msgmax=1048576
sudo sysctl -w kernel.msgmnb=1048576
```

### Запуск скрипта:
```
./test.sh <file_name>
```

## Результаты и выводы

Замеры выполнены на процессоре Intel Core Ultra 9 285H. Передавался файл `input.bin` размером 4 ГиБ. Для каждого способа передачи проверены три размера буфера: 8 КиБ, 64 КиБ и 1 МиБ, по три запуска на каждый размер. Время измерялось через `time` (`real`) и включает чтение и запись файлов. После каждого запуска происходило сравнение MD5 входного и выходного файлов; во всех 27 запусках суммы совпали.

Лимиты очереди сообщений `kernel.msgmax` и `kernel.msgmnb` были установлены в 1048576 байт. Ёмкость FIFO во всех запусках составляла 1 МиБ и задавалась через `F_SETPIPE_SZ`.

| Способ передачи | Буфер | Запуск 1, с | Запуск 2, с | Запуск 3, с | Среднее, с |
| --- | --- | ---: | ---: | ---: | ---: |
| Разделяемая память SYS V | 8 КиБ | 16,445 | 17,937 | 15,949 | 16,777 |
| Разделяемая память SYS V | 64 КиБ | 9,160 | 7,032 | 9,284 | 8,492 |
| Разделяемая память SYS V | 1 МиБ | 5,387 | 5,234 | 5,195 | **5,272** |
| Очередь сообщений SYS V | 8 КиБ | 4,210 | 3,668 | 3,794 | 3,891 |
| Очередь сообщений SYS V | 64 КиБ | 2,743 | 3,193 | 2,589 | 2,842 |
| Очередь сообщений SYS V | 1 МиБ | 2,525 | 3,128 | 2,832 | **2,828** |
| FIFO | 8 КиБ | 3,916 | 3,884 | 3,775 | 3,858 |
| FIFO | 64 КиБ | 3,491 | 2,781 | 3,238 | 3,170 |
| FIFO | 1 МиБ | 2,790 | 2,956 | 3,260 | **3,002** |

У разделяемой памяти увеличение буфера дало самое заметное улучшение: с 16,777 с при 8 КиБ до 5,272 с при 1 МиБ, то есть время уменьшилось примерно на 69%. Предположительно, основная причина в синхронизации: на каждый блок в этой реализации приходится четыре вызова `semop`. Пока получатель не освободит буфер, отправитель не может читать следующий блок. При большом буфере таких ожиданий и вызовов семафоров меньше, но даже с ним этот вариант оказался медленнее очереди сообщений и FIFO.

У очереди сообщений переход с 8 до 64 КиБ уменьшил среднее время с 3,891 до 2,842 с, примерно на 27%. При увеличении сообщения для передачи того же файла нужно меньше вызовов `msgsnd` и `msgrcv`. Однако переход с 64 КиБ до 1 МиБ уже почти ничего не изменил: среднее время составило 2,828 с.

У FIFO среднее время уменьшалось с ростом буфера: 3,858 с при 8 КиБ, 3,170 с при 64 КиБ и 3,002 с при 1 МиБ. Между 8 КиБ и 1 МиБ разница составила примерно 22%, а между 64 КиБ и 1 МиБ — около 5%. Вероятная причина ускорения — снижение затрат на системные вызовы: большой буфер позволяет передавать тот же объём данных меньшим числом операций `read` и `write`.

Итого лучшие средние времена передачи: очередь сообщений — 2,828 с, FIFO — 3,002 с, разделяемая память — 5,272 с. Для всех трёх способов лучший результат получен при размере буфера 1 МиБ.
